# Control split map

The assigned modules create cycles. The proposal below removes them with small item moves and one module move. The resulting order is package, release, environment, then development. The cycles come from package application locks, policy projection, chart reading, database connections, and platform UI uploads. Evidence: `crates/control/lib/src/apply_package.rs:255`, `crates/control/lib/src/verification_policy.rs:79`, `crates/control/lib/src/release_chart.rs:28`, `crates/control/lib/src/schema_baseline.rs:9`, `crates/control/lib/src/web_artifact.rs:659`.

The owning audit records the coupling problem and the wider crate map. Its recorded control decision remains deferred. This report applies the later four-crate assignment supplied for this task. Evidence: `docs/audit/coupling.md:101`, `docs/audit/coupling.md:119`, `docs/audit/coupling.md:310`, `docs/audit/coupling.md:339`.

The tables classify current code. A mixed module needs separate decision and effect modules within its target crate. Pure functions accept facts and return values or plans. Effect functions read external state or execute plans. This follows the separation documented by run-state and provisioning. Evidence: `crates/execution/run-state/src/lib.rs:5`, `crates/control/provision/src/lib.rs:11`.

In section (a), paths are relative to `crates/control/lib/src/`. Thus, `apply_package.rs:255` means `crates/control/lib/src/apply_package.rs:255`. Counts include embedded tests. Directory counts include descendants. The inventory contains 73,675 lines, including the 204-line development script. Directory rows overlap their child rows.

## (e) Proposed dependency lint rule

The current script uses reason dictionaries, offline normal dependency trees, `require`, and one error handler with exit code 65. Extend that structure. Keep the existing execution boundaries intact. Evidence: `tools/repo-lint-dependencies:7`, `tools/repo-lint-dependencies:87`, `tools/repo-lint-dependencies:95`, `tools/repo-lint-dependencies:124`.

Proposed rule text:

> Pure code accepts supplied facts and returns values or plans. Pure code has no PostgreSQL driver, Kubernetes client, Helm execution wrapper, OCI client, or owned-command dependency. Pure code performs no filesystem, network, or process effect. Pure code does not call `std::env::var` or `std::env::var_os`. Only code under `#[cfg(test)]` is exempt. A `test-util` feature alone gives no exemption.

This extends the existing crate-level boundary model to module-level ownership. Run-state already separates decisions and SQL from database effects. Provisioning already separates SQL rendering from application. Evidence: `crates/execution/run-state/src/lib.rs:5`, `crates/control/provision/src/lib.rs:11`, `crates/control/provision/src/apply.rs:9`.

PURE_REFUSED = {
