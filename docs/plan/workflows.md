# Workflows

## 1. What a workflow is

See [environment workflows](../architecture/execution.md#environment-workflows) for workflow identity, authoring, enablement, and manual admission.

Vocabulary, one meaning each:

- **workflow**: the definition — graph, trigger, `execution_type`, `execution_role`, `enabled`.
- **run**: one execution of a workflow, a row in `wamn_run.runs`.
- **node**: a compiled wasm component the graph calls — a released operation of the application or a platform node — pinned per environment by digest.
- **route**: a single operation served on the request path. Not a workflow.

Intended uses: reporting (long runs, start cost irrelevant); side effects (send a mail when a record changes); record-state automations (on submit, decide who must approve, validate externally, notify). Performance of this path is not a design driver.

A workflow is not a second application-composition model. The rules that move a record between states are application operations; a workflow coordinates separate operation calls.

## 2. Rulings

| # | Ruling |
| --- | --- |
| R1 — One shape | Every workflow is a graph run by the router and the run queue under a run row. A single-operation workflow is a one-node graph. The in-process walk with no row (`RegistrationDelivery::Walk`) is removed. |
| R2 — Nodes pinned per environment | `environment.k` pins the exact node versions an environment may run, one per `(name, major)` (R7), in the connector lifecycle. A pin selects nodes for new runs only: a run freezes the exact digest of every node it resolved at admission (`wamn_run.runs.node_digests_json`) and executes those bytes; a re-pin never changes a queued or reclaimed run and is always allowed. The active pin and the retained bytes are different things: a digest's artifact is retained — pulled by digest, as any component is — until no unfinished run names it; retiring (deleting) an artifact is what is refused while such a run exists, never a re-pin. No palette table, no selection row. Admitting a node is an edit and an apply, never a release. |
| R3 — Execution identity | Every environment has one `user` row `type = service`, name `workflow`, created with the environment. It holds roles like any user, granted by admins. A workflow carries `execution_type = role \| invoker` and `execution_role` (the role when the type is `role`; null when `invoker`). A run with type `role` executes as the `workflow` user with `execution_role` as its active role — the one-active-role rule applied to a run as it is to a session; the run row carries it as the token does. `invoker` on a manual or attached trigger executes as the calling user with their active role, taken from the authenticated session that made the request — never from a parameter. A manual start is therefore a host route (`workflow.start`, an operation in the application's ACL) admitted by the host against the release it is serving; `wamn-ctl workflow start`, tests and automation all call that route with a session or service-principal token. There is no other start path: the project-admin database start under a supplied service principal is retired with the candidate request. The run row carries the invoker's user id and role, which is new: today `queued_service_caller` accepts only a service principal. `invoker` on an event or schedule trigger: the caller is the system, so the run executes as the `workflow` user with `admin` active, under the same enable rule as `role = admin`; one meaning for the picker — run as whoever caused this. Enable checks two things: the enabler may assign the role (holds it or is admin), and the `workflow` user holds it; `invoker` on an event or schedule is assigning admin and needs admin. Revocation boundary: every node's operation call checks the grant through the host's auth memory as a request would, not through a snapshot taken at claim; a role revoked mid-run refuses the next node under the same semantics a request gets — the revocation drop over NATS reaches every host as it is delivered, and a host that missed the drop is bounded by the memory's TTL. No stronger guarantee is claimed. This changes the router, which today reuses the claim-time grants across nodes. A run records two separate facts: **executed as** (the principal and active role it used) and **invoked by** (what caused it: the session user for manual and attached triggers; the delivery id and, when the triggering change's history row carries an actor, that user, for events; the schedule and due time for schedules), as `invoked_by` and `invoked_by_user_id` on the run row beside the executing principal. `updated_by` on a record is the executing principal: the `workflow` user for type `role` and for callerless `invoker`, the calling user for manual and attached `invoker`; which workflow and which invoker caused the change is one join away through the write log's delivery id. The ACL is unchanged: create, read, update, delete per model plus named operations; a workflow that changes a record runs as a role holding `update` on that model. |
| R4 — Synchronous answer, separate transactions | A request may run several operations and several workflows. A workflow attached to an operation runs after that operation commits, in-process, with a bounded wait; its `respond` terminal is the response. Every operation it calls opens its own transaction; no workflow runs inside a database transaction. On timeout the request answers with the record as it stands and the run finishes on the queue — one owner at a time: the request path releases the run's lease before the queue may claim it, and the queue resumes from logged node outcomes (R5); until the effect writer exists the attached trigger does not ship. The record is the source of truth; a user decision (`approve`) is a user operation that starts the workflow again. No run waits on a user. |
| R5 — Edges are calls, nodes are logged | An edge is a separate invocation. Resume state is the graph plus the node log: a side-effect node writes an attempt before it runs and an outcome after (`wamn_run.effect_attempts`, `effect_attempt_outcomes`, keyed by run, node, occurrence; the tables exist, the writer does not), and the outcome row gains the node's output (`output_json`, bounded; today the row holds only `success` or `error`). The router recomputes the frontier from the graph and the log: a node with a success outcome is skipped and its logged output is its result; branch decisions are node outputs like any other. Per workflow: `on_failure = resume \| restart \| manual` (resume is the default; manual means no automatic rerun). Output logging is required for every node whose output feeds a later node when `on_failure = resume`; a node may opt out only under `restart` or `manual`. Failures are always logged. An attempt with no outcome is effect-uncertain: the node re-runs only if it carries an effect key, otherwise the run parks as `effect-uncertain`. Until the writer and the output column exist, a reclaimed run restarts at the first node and external effects are at-least-once, exactly as released workflows behave today; nothing in this design worsens that, and the attached trigger and `resume` wait for the writer. Retention is an environment policy (a retention field beside the durability class in `wamn_run.environment_policies`), not a workflow field. The effect tables refuse `DELETE` by trigger (`reject_immutable_effect_fact_change`) and have no FK to `runs`; retention therefore gets its own authorized path — a `SECURITY DEFINER` function owned by the retention role that the trigger exempts — never a plain delete. Compensation is an edge to an application operation. |
| R6 — Events are rows, consumers are per entity | An event trigger is a row: `source_package` and `entity` (one captured model; the package qualifies the name, as today's registrations do), `ops` (a subset of `insert`, `update`, `delete`, today's vocabulary), optional `condition` over the old and new image. Consumers are a property of the application's captured entities, created at env apply from the installed schema, one per entity; nothing in JetStream is created or removed for a workflow. The materializer is one per environment, always rendered, reads enabled trigger rows and filters each message by package, entity, op and condition. Two workflows on one entity are two rows, one consumer. Fan-out: for one message the materializer admits one run per matching trigger in one host-owned transaction — a batch admission that is new; today's `admit_event_run` admits one run per call — each with idempotency key `(workflow_id, delivery_id)`, and acks after that transaction commits; a redelivery re-admits idempotently, so a partial failure repeats nothing. Enable boundary: enable reads the entity stream's last published sequence (stream tail, not a consumer's position) and writes it into the trigger row in the enabling transaction; the materializer matches only messages whose stream sequence is greater. The read and the commit are not atomic: a message published between them has a greater sequence and starts the workflow, which is the safe side. This is publication order, not commit order: a change committed before enable but published after it (CDC lag) does start the workflow, and a change published before enable never does. Stated and accepted; a commit-ordered boundary would need the history position on the message and is not proposed. An operation that today declares a `registration` in its package (a custom operation declared as an event handler) is an operation like any other; the trigger that starts it is a workflow row authored in the environment. |
| R7 — Versioning and deprecation | Node versions are semver, and every published digest is a new version. Publish computes the bump the declaration requires and refuses a smaller one: patch = declaration unchanged; minor = additive only (a new optional parameter or port); major = anything else. A workflow names a node by name and major. `environment.k` pins one exact version per `(name, major)`; a patch or minor bump is a re-pin of that slot and every workflow on that major moves with it; a new major is a new slot, coexisting. A major may be marked deprecated: the editor shows it, enabling or editing a workflow that names it warns, unpinning it is refused while an enabled workflow names it. No range is resolved at run time: the environment holds one digest per major and the run pins it. Operations are not versioned; the release is their breaking surface, and `wamn-ctl env apply --dry-run` against a candidate release is the early check, runnable any time, writing nothing. |
| R8 — Workflow identity | A workflow is keyed `(env_key, environment, application, workflow_id, version)`; a package version is not part of its identity. A version row is immutable (graph, hash, trigger, `execution_type`, `execution_role`); `enabled` is its one mutable field, and at most one version of a workflow is enabled at a time — a partial unique index on `(env_key, environment, application, workflow_id) WHERE enabled`; enabling a version disables the previous one in the same transaction. A start selects the enabled version. Disabling stops new starts only; queued and running runs finish under the version they pinned. Its graph names operations as `package.operation`; admission resolves them against the release the run pins. A package upgrade that keeps those operations does not touch the workflow; one that drops or changes them is refused at `env apply` by workflow and node. |
| R9 — No workflow in a package | A package ships no workflows and no triggers; a custom operation's `registration` leaves `wamn.k`, and the operation stays. The two shipped today (WMS label, NetSuite pull) become environment data authored in their environments. A package may later carry a workflow template; an instance exists only when an environment asks for one and is the environment's from then on. Interim exception: `publication/wirings` selects node build inputs and connection aliases only. Tests read those files to author environment workflows. These files never supply released workflows, catalog wirings, attachments or runs. Epic 4 deletes them when `environment.k` pins replace them. |

Enable, disable and change of a workflow take the environment's lifecycle lock (`environment/lock.rs::LifecycleLock`, `pg_try_advisory_lock`, shared with `env apply`): while an apply holds it, enable is refused with "apply in progress" and the caller retries; the lock does not queue. So no workflow becomes enabled between the apply's check and its Helm write. Authority lifetime: the enabler's authority is checked at enable and change. An enabled workflow belongs to the environment, not to a session. Revoking the execution role's permission refuses the next protected call under the existing per-operation check. No author query on every start. Deploying logic that runs on every record change is an admin act; a tenant that wants a narrower publisher makes a role holding the enable operation.

Logic inside a workflow — shaping between nodes and conditions — is configuration, never business-authored code. Whether that configuration is an expression language (JSONata is the one node that exists), a library of small typed nodes, or both, is decided with the editor, not here.

## 4. Epics

### Epic 2 — schedules from rows

Run the [wamn-dev cutover](../operations/queued-automation.md#cutover-the-netsuite-pull) and a kind case for the NetSuite pull and the rest_connector item as schedule rows.

### Epic 4 — effect writer and node publication

The effect writer with `output_json`, effect keys, the uncertain rule, resume and retention's authorized deletion (R5); then node publication and `environment.k` pins per R2 and R7, and the attached trigger (R4). Order inside this epic is decided when it is scoped.

### Invariants and checks

| Invariant | Check |
| --- | --- |
| A run executes the bytes it froze | admit a run; re-pin the node to a new minor: allowed; the run executes the frozen digest; a new run executes the new one; retire the old artifact while the run is unfinished: refused |
| A run is exact and durable | queue and reclaim; hash, components, inputs and digest unchanged; a host of another release cannot claim it; a reclaimed run restarts at the first node until the effect writer lands, then resumes at the first node without a success outcome |
| A deprecated major stays until unpinned | mark a major deprecated: enable of a workflow naming it warns and succeeds; unpin it while one is enabled: `env apply` refuses naming the workflow; disable the workflow: unpin succeeds |
| A bump is what the declaration requires | publish a removed port as a minor: refused; as a major: accepted; publish unchanged bytes under an existing version: refused |
| A minor re-pin moves workflows safely | workflow on major 1 at 1.0.1; pin 1.1.0 (new optional parameter); the workflow runs unchanged |

### Later

| Capability | Direction |
| --- | --- |
| Attached trigger (R4) | epic 4, after the effect writer. Trigger row `after = <operation>`, `wait = <bound>`. The entry runs the workflow after the operation commits, in-process, under a run row and a lease; `respond` is the response; on timeout the entry releases the lease and the queue resumes from logged outcomes. The approval and external-validation uses need this. |
| Node publication | epic 4. digest-addressed nodes published without a consuming application, pinned per `(name, major)` to an exact semver in `environment.k`; the wiring node reference gains the node's major (today the join is on the WIT interface version, which every node shares — verify); the semver bump rule enforced at publish from the declaration hash; a host missing an import refuses until the platform version that has it is applied. |
| Editor and run history | `apps/platform_ui`, server-authorized routes, forms from node declarations, run list per workflow, the failed node with its input, retry and cancel. The expression-language-or-nodes choice is made here. |
| Run retention | completed and failed runs are deleted by age, per environment policy (a retention field added to `wamn_run.environment_policies`, the `wamn_run_retention` role); attempt rows are deleted by the same age through the authorized function in R5, since nothing cascades and the trigger refuses a plain delete; failed runs keep longer. Volume is a tenant's choice: more runs and longer retention cost hardware, not design. Replay-reachability GC waits until something replays. The `condition` on an event trigger is what keeps a hot entity from starting a run per update. |
| Effect writer, retry and compensation | epic 4. the writer for `effect_attempts` and `effect_attempt_outcomes` with `output_json`, effect keys, the uncertain rule and resume (R5); per-node retry count over the existing backoff; `on_failure` and output logging; failure edge to a compensating operation. Confirm first what the schema comment's "execution remains hard-refused" refuses today. Precondition of the attached trigger. |
| Reports, files, mail | workflows over released reads, `http-request`, `http-page`, `file.put`. No platform PDF, template or mail service. |
| Seeding from a package | a package may carry a workflow **template**; an instance is created only when an environment asks (a line in `environment.k`), owned by the environment from then on, never overwritten by apply. R9 stands: a package ships no workflow instance. Until this exists, an integration's operational workflows (the NetSuite pull) are authored in the environment by `wamn-ctl` or the UI. |

## 5. Cost of events from rows

See [event admission](../architecture/execution.md#workflows) for consumers and the materializer.

The materializer can attach to an entity's consumer only while an enabled trigger names that entity.
It can detach when no enabled trigger names the entity.
This option changes attachment only. It never creates or retires a consumer.
Measure the busiest captured entity against the consume-and-filter cost before adding this option.

## 6. Assumptions

| Assumption | Verify | If false |
| --- | --- | --- |
| one row read per host per tick is acceptable | enable a schedule on a running host; it fires at the next due time; the tick's query cost is measured on a host with many schedules | reload on an enable/disable message over event NATS instead |
| an in-process run hands over to the queue on timeout under one lease, resuming from node outcomes | a run that times out at node two releases its lease, is reclaimed, skips node one and completes with no duplicate external effect | a timed-out attached run is failed and the row event starts a fresh one; the request answers with the record |

## 7. Exclusions

No release carries a workflow; no compatibility ranges; no business-authored wasm or SQL; no workload per workflow; no second router, scheduler, queue or identity model; no palette table; no cross-edge transaction; no run that waits on a user; no PDF or mail service; no persisted record without a distinct fact and a reader.
