# Addendum: the authentication_event table (E4.12)

This addendum serves the owner ruling of 2026-11-26 on Epic 4 question 1. It was read at commit `9c5f76d9d`. F means read in the code at that commit. I means proposal. A read-only agent wrote sections 1 to 8 below. Root checked the immutability trigger, the forwarded IP source and the rate limits. After the owner rules on the questions at the end, bead E4.12 starts.

The ruling, as decided: the table is in the system database, and identity writes it. Rows are immutable, with full retention. `event_type` and `outcome` are foreign keys to lookup tables. A row keeps the IP address and the attempted email, also for an unknown user. The table loads through the bootstrap SQL only.

Summary of the proposal (I):

- Table `identity.authentication_event` in `deploy/sql/system-schema.sql`, with lookups `identity.authentication_event_type` and `identity.authentication_event_outcome`. Outcome has `success boolean NOT NULL`.
- 13 event types, from password sign-in to the two NATS credential exchanges (section 2). 39 outcomes (section 2).
- Columns from `platform_event`, plus `attempted_email_key` (the throttle digest, for search), `ip_source` and `peer_ip_address` (provenance), `requested_org`, `login_id`, `session_jti`, `request_id` and `workload` (section 3).
- The existing `provisioning.reject_immutable_row_change()` trigger refuses UPDATE and DELETE (`deploy/sql/system-schema.sql:665`) (F).
- Three partial indexes: failed sign-ins by email key, a principal timeline, an org timeline. If you name a read by IP, an IP index is added (section 5).
- Grants: identity's issuer group gets INSERT only, with an RLS insert policy. No reader except the platform operator for now (section 6).
- The tables stay out of the history installer and the pruning (section 7).

One fact needs your attention (F). Identity takes the client IP from the last `x-forwarded-for` header (`services/identity-service/src/lib.rs:243`). It accepts that header from any caller that its ingress policy admits. That policy admits the web proxy, host pods, control and workers (`deploy/charts/platform/templates/identity-network-policy.yaml:11`). So a host pod, which runs tenant code, can set the IP that a row records. Question 4 covers it.

## 1. Identity write points

**F** Identity dispatches seven password POST routes and six internal POST routes. For the password routes, it uses the last address in the last `x-forwarded-for` header, falls back to the TLS connection peer, and returns 400 for a malformed forwarded address. The web proxy selects an address by configured trusted hop count and overwrites the header with one address. The chart defaults to one trusted hop. Identity itself accepts the header without authenticating the sender as the web proxy. The internal routes branch before that check and receive the socket peer. `services/identity-service/src/lib.rs:224`, `services/identity-service/src/lib.rs:405`, `services/web/src/lib.rs:304`, `services/web/src/lib.rs:327`, `deploy/charts/platform/values.yaml:211`

**F** The identity ingress policy lists the web proxy, hosts, control and workers. **I** The forwarded address is useful evidence with provenance. The chart alone cannot establish that an incoming header came from the web proxy or that the deployed proxy chain selected the actual client. Preserve the socket peer alongside any forwarded address. `deploy/charts/platform/templates/identity-network-policy.yaml:11`, `services/identity-service/src/lib.rs:243`, `services/web/src/lib.rs:327`

Each proposed write below changes **identity behaviour**. Keep the existing HTTP status, headers, cookies and JSON. ## 8. Risks

- **I** Email and IP retained indefinitely make the table, its indexes and its backups sensitive. Arbitrary email input may also contain someone else’s address or a pasted secret. Keep the original value out of operational logging, bound it by the existing request size, use fixed failure summaries and restrict reads to the selected audience. `docs/plan/review-restructure.md:587`, `services/identity-service/src/password.rs:30`, `services/identity-service/src/password.rs:373`, `crates/identity/src/identity/password.rs:21`
- **F** The platform journal propagates a failed `started` append before dispatch. Control logs failed terminal appends while preserving the existing refusal. A worker reports an append failure after successful work, and logs an append failure after failed work. Org provisioning also reports journal errors. **I** For authentication, make successful session issuance atomic with the event. Preserve revocation, replay handling and undeliverable-token invalidation even if the append fails. Use a bounded append for refusals and a redacted operational warning when the database cannot record one. A database outage can take down both authentication and its SQL audit sink. `crates/platform-install/src/platform_event.rs:81`, `services/control/src/control_route.rs:255`, `services/control/src/control_route.rs:260`, `services/control/src/platform.rs:193`, `crates/platform-install/src/provision_org.rs:72`, `crates/identity/src/session_exchange.rs:99`, `crates/identity/src/password_requests.rs:133`
- **F** Password admission uses 60-second windows with limits of 120 globally, 20 per source and five per account bucket. Rejected attempts keep updating a saturated counter. The global/source check precedes JSON parsing. **I** At 120 admitted attempts per minute, one row per admitted attempt alone could produce roughly 173,000 rows a day. One row per denial scales with attempted traffic, and successful issuance can add companion rows. Record the first denial per exhausted bucket per window if the owner accepts this coverage. The existing bucket update is the place to detect that transition. The global/source refusal normally has no email because the body is still unread. `services/identity-service/src/password.rs:132`, `crates/identity/src/password_requests.rs:21`, `crates/identity/src/identity/issuer.rs:81`
