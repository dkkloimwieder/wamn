# Platform and application deployment plan

@D Kloimwieder

Status: single authority. Evidence cites the repo's `main` by file and symbol; fact unless marked inference. Rulings R1 to R22 (§9) record what was decided and why; §3 lists the assumptions they rest on and how each is checked.

## How this plan is worked

- This is the one authority for how an application is authored, built, packaged, published, qualified, deployed, upgraded, rolled back and removed on wamn. Where it differs from `docs/architecture`, `docs/plan` or `docs/operations`, those are updated by the epic that lands the difference.
- Epics may run in parallel when they share no files and no migration (owner ruling 2026-10-09). Each running epic is scoped into issues; the epics not yet started in §17 are direction, not work, and have no issues. Merges to `main` are serial. Migration numbers are assigned at merge, not in the lane. Before merge, a lane runs every live test target that touches its files. The test of this document is that scoping: an epic must be scopable into fully specified issues from this document alone, each issue naming its files, the §2 invariants it makes true and the §3 checks it runs. If it cannot be, the document is insufficient; the gap is reported with the section that fails to answer, and nothing is guessed.
- An epic is a few large issues with every foreseeable question answered in the issue; an agent stops and asks on an uncovered fork and never decides it.
- The five shared contracts (§17.1) are written down and accepted before Epic 1 is scoped.
- Owner rulings this plan rests on are listed in §2.

## 1. Goal

Four units, each with one name, and one verb between each:

```
package source   apps/wamn_wms/            git
package          wamn_wms@2.2.0            (id, version): the lineage name
package artifact sha256:…                 OCI, referencing its components by digest, verified at push
release          sha256:…                 OCI manifest naming packages and components by digest, qualified in OCI
application      a release deployed in an environment
```

```
wamn push-package                  # builds when stale; one verified package artifact by digest
wamn publish-release               # composes verified packages; one manifest by digest
wamn env apply <environment.k>     # analyse, then one helm upgrade, toward what the document declares
```

The author writes what only the author knows; the generator derives the rest at build and nothing derived is committed. A package is bytes in OCI, tenant-free. A release is a content address: the same bytes have the same digest in every environment. An environment is one Helm release, the `release` chart that `apply` upgrades, plus a CNPG `Database` CR the verb applies. Kubernetes and the wasmCloud operator own rollout, readiness, rollback and history. The project database owns what is installed in that environment and nothing about what runs where. A deployment is three parts in one verb under one lock: wamn's semantic writes (the document's rows, the package stage), one deployment write (one Helm operation), and post-deployment observation (readiness, the check). No Postgres record of the deployment itself.

One test decides every concept: if Kubernetes and wasmCloud were replaced by another scheduler tomorrow, would this concept still be part of wamn's application model? Yes, it stays in wamn (package, release, schema compatibility, migration, permission, binding, qualification). No, it belongs below wamn (readiness, rollout sequencing, placement, apply order, restart procedure).

### 4.3 Helm hooks, waits and rollback

- Hooks: `pre-install`, `post-install`, `pre-upgrade`, `post-upgrade`, `pre-rollback`, `post-rollback`, `pre-delete`, `post-delete`, `test`. A `pre-install` hook "executes after templates are rendered, but before any resources are created". Helm waits until a hook is ready before proceeding; if a hook fails, the release fails. Hook resources "are not managed as part of the release" and are not deleted on uninstall; `hook-delete-policy` (`before-hook-creation`, `hook-succeeded`) controls that. ([Chart hooks](https://helm.sh/docs/topics/charts_hooks/))

([helm upgrade](https://helm.sh/docs/helm/helm_upgrade/))
- `helm rollback`: "rolls back a release to a previous revision"; "If this argument is omitted or set to 0, it will roll back to the previous release"; `--no-hooks` prevents hooks from running; the hooks that run are `pre-rollback` and `post-rollback`, never `pre-upgrade`. ([helm rollback](https://helm.sh/docs/helm/helm_rollback/))

### 4.4 CloudNativePG `Database`

- Required fields `spec.name`, `spec.owner`, `spec.cluster.name`. `databaseReclaimPolicy`: `retain` (default), "the database remains in PostgreSQL for manual management"; `delete`, "the database is automatically removed from the cluster" when the object is deleted. ([Declarative database management](https://cloudnative-pg.io/docs/devel/declarative_database_management))

### 4.5 OCI referrers

- The Referrers API, `/v2/<name>/referrers/<digest>`, returns an image index of manifests "with a `subject` field that specifies the value of `<digest>`"; registries without it are served by the fallback tag `sha256-<encoded digest>` returning the same index. ([OCI distribution spec](https://github.com/opencontainers/distribution-spec/blob/main/spec.md)); cosign stores signatures and attestations this way ("Signatures use the OCI 1.1 referrer specification", [cosign](https://docs.sigstore.dev/cosign/signing/signing_with_containers/)).

## 6. Authoring

Rule: the author writes a fact once, in the place that owns it. The SQL owns what tables a statement touches. The schema owns column types, checks and stamps. The manifest owns names, operations, inputs, results, errors and workflows. The generator derives the rest and refuses nothing it can compute. This flips four rows of the retain/derive table in `data-access.md §Application declarations` (R9).

### 6.1 Derived or authored

| Today | After |
| --- | --- |
| `relations` declared per command; the generator diffs them | derived from the statements by the lexer in `generate/validation.rs::validate_delete_target`; written into `wamn.json` and `data-access.json`. An author may declare `constraints` (constraint name → error) on a command; nothing else. |
| `authored_sql` with one file per sort variant | for a generator-owned model query (one table, declared filters): `sort` and `filters` only; the generator emits the variants it already emits for `location` and `product`; `authored_sql` is refused there. For a query the generator cannot write (join, aggregate, window): `authored_sql` with explicit variants as today. The generator never rewrites SQL it did not write. |
| statement `parameters` and `row` with types | statement name, `fetch`, parameter names: `parameters = ["packaging_id", "to_location_id", "occurred_at"]`. Types and nullability come from `.sqlx` at build (§7.1). A declared type is optional; declared, it overrides the derived one where narrower (a non-null row field on a nullable column, the contract `data-access.md §Application declarations` keeps) and is refused where wider. |
| `raw_body_maximum`, `envelope`, `canonicalization`, `constraint_errors`, `idempotency_conflict` detail per command | defaults on `manifest.Command` in `manifest.k`; `idempotency_conflict` derived by the reader with the other shared details (`manifest.rs::OPERATION`). Written only to change. |
| `enum_fields`, `min_lengths` mirroring CHECKs; stamp columns in `server_owned_fields` | read from the schema the generator already verifies against. `enum_fields` stays only to name a value set the CHECK does not carry. |

Authored, because only the author knows it: model names and which operations each exposes; writable fields and value restrictions per operation; command inputs, results, business errors and their details; statement names, fetch mode and parameter names; attachments, wirings, registrations; `predecessor_version` and `upgrade_stage`. Measured on WMS: `wamn.k` from 696 to about 300 lines; `query/` from 9 files to 1.

### 6.2 What the author controls

Nothing an author can customize today is removed; what goes is the second copy of a fact stated elsewhere.

| Customization | Today | After |
| --- | --- | --- |
| a custom command or projection: inputs, result, errors, every statement | `wamn.k` + `command/*.sql` | the same; statement types, `relations` and fixed defaults no longer spelled |
| a query the generator cannot write | `authored_sql`, one file per variant | the same |
| a narrower contract than the schema | declared `row` types, `enum_fields` | the same, now optional; narrows, never widens |
| constraint names mapped to errors | `constraints` on a relation | `constraints` on the command |
| backend code: the Rust component, nested calls, an overlay composed on a base | `component/`, `base_dependencies` | the same; wit and bindings read from `target/` |
| routes and workflows | `publication/` | the same |
| frontend: screens, forms, tables, the shell | `web/src`, importing `@wamn/<app>-client` | the same; the client package resolves to `target/wamn/<package>/client-ts` through the pnpm workspace |
| a staged schema change | `upgrade_stage` with migration SQL, backfill SQL, pre- and postconditions | the same (§10.4) |
| editing a generated file | refused by the byte check | not in git; same rule, no check |

## 7. Build and push-package

### 7.1 wamn build

One verb replaces `tools/build-components` and `materialize`. Everything it writes goes to `target/wamn/<package>/`; nothing under `generated/` is in git, `wamn.json` included (R10). The package artifact carries the canonical `wamn.json`; `wamn inspect <digest>` and `wamn diff <digest> <digest>` show it; reviewers diff `wamn.k`. In order, against a fresh verification database:

1. compile `wamn.k` to the authored form: every fact the author stated, no derived field; this is not yet `wamn.json`;
2. migrate the verification database to the package's dependency closure: the base's migrations first for an overlay, then the package's;
3. describe every statement against it through SQLx's PostgreSQL describe path, as a library call: parameter types, result column types, and SQLx's nullability inference (catalog constraints plus `EXPLAIN VERBOSE` for outer joins). PostgreSQL's own RowDescription carries no nullability, so this is not a raw `PREPARE`, and no verifier crate is generated in this pass;
4. derive statement types and `relations` from the described statements and the lexer; apply the author's narrowing declarations (§6.1);
5. emit the canonical `wamn.json`: authored facts plus derived facts, RFC 8785, hashed once;
6. generate wit, bindings, SQL, client, data, the native verifier into `target/wamn/<package>/` from the canonical manifest;
7. `cargo build` the component with the generated wit and bindings included from there; compose with the base for an overlay, checking the pin (today publication checks it, `building.md §Native programs and app components`); `cargo sqlx prepare` the generated verifier against the same database, as the independent check that the bindings compile against what was described;
8. `pnpm build` the web client with `@wamn/<app>-client` resolved to `target/wamn/<package>/client-ts` by the workspace;
9. write `build.json`, the content receipt: source and input digests, exact dependency package digests, generator and toolchain identity, output digests.

Two passes, because the derived facts belong in the canonical manifest and the consumers are generated from the canonical manifest: pass one describes SQL and emits `wamn.json`; pass two generates everything from it. `.sqlx` is build output, not source. `materialize check` and `refuse_unexpected` go; the generator's correctness is tested in `crates/schema/generator/tests` with fixtures, once. TUI output stops until the TUI is rebuilt. `wamn build` is the developer's check and writes nothing outside `target/`.

### 7.2 push-package

`wamn push-package` is the one verb that makes a package exist (R11). It reads `build.json`, a content receipt (source and input digests, exact dependency package digests, generator and toolchain identity, output digests), and rebuilds when the input part of the receipt differs from the tree; never by timestamp (R10). Then:

1. push each component as its own OCI artifact under its content digest, the same object and media type `push-component` pushes today (`component_artifact.rs::reference`), because the wasmCloud operator pulls `components[].image` as an OCI reference (§4.2);
2. push the package artifact: an OCI manifest whose layers are the canonical `wamn.json`, the migrations, the attachments, the web client build, and the admitted component descriptors (interface version, imports, effects, operations, dependency graph; today's `publication/components.json` rows), each bound to its component digest, and whose annotations name every component digest. The package artifact references components; it does not contain them. `publish-release` reads the descriptors from here, which is what it reads from `component_library` today (`publish_release.rs::SELECT_COMPONENT_FACTS_SQL`);
3. record the verification: the build completed against the dependency closure, so every statement described and every generated output matches the manifest; the staged-upgrade policy holds against `predecessor_version` (`package-upgrade.md §7.3`); write `verified_at` on the artifact registry.

Both kinds of object are tenant-free. Which tenant installed a package is a project-database fact. The OCI layout here is shared contract A (§17.1).

### 7.3 Overlays

An overlay is a package with `base_dependencies` pinning the base's `(id, version)` and component digest (`overview.md §Application ownership`); its component is composed with the base at build (`building.md §Native programs and app components`). Verification runs at the exact closure, base migrations first: environment-independent, dependency-exact. Definition ownership on shared relations stays in `catalog.package_definition_owners` in the project database; it is read by synchronization, the run plane and staged upgrades (`apply_package/synchronization.rs`, `definition_ownership.rs`) and is per definition, not per package.

### 7.4 What goes

`push-component` as a verb; `apps/target/components.json`; `component_library` and `component_digest_owners` (R3); `package-identity.json`; `manifest_sha256`; the `catalog.packages` and `package_migrations` copies in the system database; `materialize.rs` check mode; the per-application `verify_sqlx_metadata` test; 26,494 committed lines per application.

## 8. publish-release and qualify-release

### 8.1 publish-release

`publish-release` composes verified package artifacts into a release manifest and pushes the manifest to OCI. It builds nothing and pushes no package; an unverified package artifact is refused. It reads each component's admitted descriptor from the package artifact (§7.2), which is what it reads from `component_library` today (`publish_release.rs::SELECT_COMPONENT_FACTS_SQL`). The manifest is the schema of §5 (R1): no tenant, environment, route host, image or assigned number. The route host injection of today (`publish_release/attachments.rs::read_authored_attachments`) leaves publish: an http attachment is a path, a method, an auth policy and an operation. This is a runtime change too: `flow_http_routing` takes its routes from release attachments (`flow_http_routing.rs::routes`), so the router learns the host from the http workload's own config (`config: {host: …}`, already on the WorkloadDeployment) and matches the logical route under it; that change is in Epic 4. Authorization is decided here as today. `prepare-release`, `push-release-manifest` and `publish-qualified-release` go; `publication/` stays the name of the authored attachments directory.

### 8.2 qualify-release

`qualify-release <digest> <release chart version>` takes a release digest and the chart version whose defaults name the platform image set to test it on (R15: the host digest and the platform role component digests, derived from the chart, never restated on the command line; today's key also holds gates and identity, `delivery/selection.rs (module doc)`, and drops them, R12) and a kind cluster. It pulls everything by digest, runs the cluster cases named for the package set (`delivery/qualification.rs::application_for`, unchanged) with the platform-owned, versioned qualification runner, and pushes the result as an OCI artifact whose `subject` is the release digest and whose payload names the image set it ran on and the runner that ran it (§4.5). The runner is provenance, not part of the key: its backward compatibility is a platform invariant, so a new runner invalidates no qualification (R15). No checkout, no rebuild-compare, no toolchain check, no result file, no `catalog.qualifications` row, no `deployment_attestations` row (R12). A qualification is reusable by any environment whose platform image set is the one it names, whatever chart version selected it; a release on a new host or role image needs a new qualification. Identity and gates are shared platform services outside the key: their backward compatibility is a platform invariant the platform's own suite proves before a platform upgrade ships, so a release never re-qualifies for them (R12). The check operation must be a read (§10.3); a write is refused here. The runner is platform-owned so release composition stays artifact-based with no single source commit behind it.

### 8.3 Verification and qualification are different facts

|  | Package verification | Release qualification |
| --- | --- | --- |
| proves | the package artifact: statements plan, generated output matches, staging policy holds | the release behaves on a platform image set: cluster cases pass |
| runs | `push-package`, against a fresh database at the dependency closure | `qualify-release`, against a kind cluster with that image set |
| recorded | `verified_at` on the system database's artifact registry | an OCI artifact: `subject` = release digest, payload = image set |
| read by | `publish-release` | `apply`, which matches the environment's image set |

The predecessor-window test of `qualify-upgrade` (§14) is a third fact: that a staged change leaves the running release valid on real data. It stays in the project database as `package_upgrade_qualifications`.

## 9. The environment

One chart per environment, `release`, one Helm release, one verb that upgrades it (R6). The chart holds Kubernetes objects only and has no hooks; every Postgres and identity step, every check and every wait is run by the wamn verb, before or after the Helm write. Every fact about what an environment runs is a Kubernetes object or a Helm value; wamn reads them and copies none (R5). The environment's own facts that render nothing in Kubernetes until a release is selected, the route host and the policy name, live on the environment row in the system database beside its policy (R2), not in a chart.

wamn's part after the write is a wait and two reads: `helm upgrade --wait` returns when the host Deployment is ready; the verb then waits on each WorkloadDeployment and runs the check (§10.3). The package stage ran before the write (§10.2); the previous release's hosts serve until the Deployment controller replaces them with pods that report ready, and its role workloads until the operator has placed the new release's; the interval between those two is the accepted window of §10.3.

### 9.1 Names and the database

The Helm release lives in the operator release's namespace, `hosts` (R6). Helm release names are bounded to 53 characters, so the name is `r-<slug>-<hash>`, where slug is the env name cut to 24 characters and hash is the first 20 hex of sha256(org, project, env), 80 bits, collision-resistant at any scale wamn will see; the full coordinate is in the annotation `wamn.environment` on every object. Every object identity in the namespace derives from that name and nothing is authored: the wasmCloud host group is the release name, so the subchart renders `hostgroup-<name>`; the WorkloadDeployments are `<name>-http` and `<name>-materializer`; the Services likewise. Two environments therefore cannot share an object name, which matters because the chart names objects after the host group and not after the release (`templates/runtime/deployment.yaml (name: hostgroup-{{ .name }})`). The same rule binds every Secret and ConfigMap the environment owns: its credential Secrets are named from the coordinate, as `workload_secret_name` already does (`provision/src/name.rs::workload_secret_name`, `<family prefix><org>--<project>--<env>`); a fixed name belongs only to a platform-owned shared object, today the TLS Secrets the operator release renders. The CNPG `Database` CR for the environment is applied by `apply` with `kubectl apply` (§12.1) and carries the same annotation; it is not a chart object because a chart around one CR is ceremony, and CNPG reconciles the CR itself (§4.4). Credential Secrets are not chart objects either: `apply` writes them after the database is ready and is their one owner; the chart references them by those derived names.

### 9.2 Chart `release`

Installed and upgraded only by `apply`.

| Template | Object | Carries |
| --- | --- | --- |
| host group | `Deployment` | host image from the chart's defaults (R15), `--release-manifest-digest`, `--release-artifact-base`, through the subchart's `runtime.hostGroups[]` whose one entry is named after the release (R6, §9.1); a stable Deployment name, so a new release is a pod-template change and Kubernetes rolls it; pod labels `wasmcloud.com/hostgroup` (the chart's) and `wamn.release=<digest, lowercase unpadded base32, 52 characters, lossless>` through `runtime.podLabels`, read by the live set; heartbeat labels `hostgroup` (the chart's) and `wamn.release`, the same value, which the operator writes onto the `Host` resource and which `hostSelector` matches; pod-template annotations `wamn.release-digest` (hex) and `wamn.environment` through `runtime.podAnnotations`, the one annotation seam the chart has; readiness probe that reports ready only after the release is loaded and compiled (`services/host/src/host.rs::run, preload_release` already gate serving on this); the SIGTERM drain in which the host stops admitting and keeps claiming until no run pinned to its release remains, with `terminationGracePeriodSeconds` rendered from the environment policy (R20) |
| workloads | one `WorkloadDeployment` per role the manifest's delivery requirements imply (R4): http when any http attachment exists, materializer when any event registration exists | named `<release name>-<role>`; the platform role component `image@sha256` from the chart's defaults (R15), `localResources.config.wamn.*` and the route host; `hostSelector: {hostgroup, wamn.release}` against the heartbeat labels above; `kubernetes.service.name`. No connection facts: the host resolves bindings from the project database per request |
| services | `Service` per http role | unchanged |

Values: `release.manifestDigest`, `release.artifactBase`, `roles[]` (name, config, service), `routeHost`, `policy` (the pod settings the policy renders: `terminationGracePeriodSeconds`, sizing), and `audit` (`actor`, `approvedBy`); the host image and the role component digests are the chart's own defaults and never in the values (R15); the host group and every object name derive from the release name (§9.1). The values and the workload config they render are a deployment projection (R2): they carry a copy of the route host because Kubernetes needs it, and nothing reads it back as the truth; the environment row stays the owner. No connection fact is in them (R22). Nobody edits this file by hand; Helm keeps it with the revision; it carries no secret. `audit` renders nothing: it lives in the values and the revision description that Helm keeps, which is where who selected and who approved are read (§11.3), and it is excluded from the equality test that decides whether the Helm write runs (§10.1 step 6). Helm history audits deployment writes; an apply that writes nothing to Kubernetes records no actor there.

The `wamn.release` label is the invariant the rollout needs: during a rolling update old and new host pods coexist, the host runs exactly one release per process (`release_manifest.rs (module doc, process lifetime)`), and a `hostSelector` on `hostgroup` alone could place a new release's workload on an old host. Requiring `wamn.release` makes that impossible; the operator reschedules the workloads when the selector changes (§4.2). The label must be in the host's heartbeat, not only on the pod: the operator lists `Host` resources by `hostSelector` (`runtime-operator workload_controller.go (MatchingLabels(HostSelector))`, `client.MatchingLabels(workload.Spec.HostSelector)`) and writes a `Host`'s labels from the heartbeat (`runtime-operator host_controller.go (Host labels from the heartbeat)`); `ClusterHostBuilder` adds only `hostgroup` (`wash-runtime washlet/mod.rs::ClusterHostBuilder::build`) and wamn's host sets only the group (`services/host/src/host.rs::run (with_host_group)`), so the host adds `wamn.release` with `HostBuilder::with_label` (`wash-runtime host/mod.rs::HostBuilder::with_label`) from its `--release-manifest-digest`. The pod label is the same value for the live set and `kubectl`; the two label keys for the group differ (`wasmcloud.com/hostgroup` on the pod, `hostgroup` in the heartbeat) and are both the chart's. A Kubernetes label value is at most 63 characters of `[a-z0-9A-Z._-]`, so the label carries the full 32-byte digest as lowercase unpadded base32 (52 characters), which is exact; the hex form is in the `wamn.release-digest` annotation and in the host's arguments. The host group is the environment's stable pool, one per environment, and its name is the Helm release name (§9.1), not an authored value: today's one group per environment with the release in its arguments (`deploy/gcp/values-host.yaml runtime.hostGroups[].extraArgs`) is the same shape with a hand-chosen name. The release is the label, not the group.

### 9.3 The platform image set

The set has one source (R15): the `release` chart's default values, which pin the host image digest and the platform role component digests; the chart version selects the set and is not the set. `apply` reads them from the chart it applies, puts them into the release values, and requires a qualification of R on them (R12). A platform upgrade that changes the set is a new chart version, followed by `apply` of the running release in each environment, which needs a new qualification because the digests changed; a chart version that changes templates only is applied the same way and needs none, because the key is the digests. One that changes only identity, gates or the operator release is neither, because their compatibility is the platform's invariant, not the release's. The set is declared by the chart that ships it and recorded by the qualification that tested it, nowhere else. Helm values are intent, not proof of running bytes; a Deployment edited by hand would differ from them until the next apply reverts it, and the plan accepts that rather than add a drift check.

## 10. Deploying a release

### 10.1 The environment document and apply

An environment is declared in one authored file, compiled to canonical JSON the way `wamn.k` is (R9, R10, R21). Everything in it is a fact the author knows; nothing in it is a step.

```
# environments/acme-wms-prod.k
environment = {
    org = "acme"
    project = "wms"
    env = "prod"
    release = "sha256:3f9c…"          # a published, qualified release; none = installed but not serving
    route_host = "wms.acme.example"
    policy = "prod"                     # registry.env_policies by name: approval, readiness budget, drain bound, sizing
    connections = {                     # connection definitions; credentials are provisioned, never declared
        erp = { type = "http", base_url = "https://erp.acme.example" }
    }
    floors = { wamn_wms = "2.4.0" }     # contract target; monotonic through lineage (R13)
}
```

Deployment configuration and nothing else: roles, members and grants are application administration in the project database with their own UI, and are not here (R18). `wamn env apply <file> [--dry-run]` is the one verb. It compares the document with what the authorities hold (§5) and does what differs: a first apply creates; a changed release deploys; a changed connection is ensured before the rollout and a removed one retired after the drain (R22); a floor that descends from the recorded one contracts when safe; `release = none` uninstalls; an unchanged document is a no-op. Nothing stores the document after it is applied: the environment row keeps the route host and policy name as columns, the project database keeps the connections and the recorded floors, Helm keeps the release. `wamn env show <coordinate>` synthesizes a document from those, for bootstrapping a file from an environment that predates the plan and for seeing what a rollback left. Copy is the same file under a new coordinate; promotion is the same digest in another environment's file. `--dry-run` prints the plan without the lock and says it describes this moment. The release is always named by its digest; a unique prefix is accepted and resolved first. The verb is synchronous: it returns when the document holds or names the step that stopped it. Lock, analyse, apply. In order:

1. Lock. `pg_try_advisory_lock(hash(org, project, env))` on a dedicated connection to the system database, held until the verb exits (R19). Held: refuse with "deployment in progress". The lock is session-level; a dead process releases it with its connection. No transaction is opened across any later step.
2. Analyse. Compile the document. Read the environment policy it names. With a release: read its manifest from OCI by the digest, the platform image set from the release chart's default values (R15), and a qualification of the release whose payload names that set (§8.2); none, refused; there is no first-release exception (R7). Read what the environment has, from its authorities, never confused (§5): the environment row, or none; the installed package versions, stage evidence, connection instances and bindings, and recorded floors in the project database, or no database; the last successful revision of the `release` chart and its values, or none; the live set, every host pod that is not terminated, by its `wamn.release` label (R20). A failed or pending revision is not a predecessor for anything.
3. Compatibility. Every declared floor equals the recorded floor or descends from it through `predecessor_version`, else refused; with `release = none`, every recorded floor is declared and none advances (R13). With a release: every active workflow passes its check against it; for every package the release names that is installed, its version is the installed version, a staged successor with a `package_upgrade_qualifications` row, or a version the installed version's stage evidence names as a tested predecessor (R17); a package not yet installed will be installed fresh from its verified artifact (R17); every recorded floor passes (R16); every connection the release's components require, from their admitted descriptors, is declared in the document, else refused by name (R22). Approval: a policy that requires it needs the applying user's role (`env_policies.rs`); the approver's identity goes into the values. The plan: the differences from each authority, the stage to run, the connection rows to add or update now and to retire after the drain, the floor to record if any, the objects that would change or that nothing changes. `--dry-run` stops here.
4. Ensure the substrate. Each step is an ensure, judged by what it observes, never by whether the row exists: insert the environment row with a fresh `instance_suffix` only if there is none (`system-schema.sql registry.project_envs`; the suffix never changes until `delete` removes the row); ensure the CNPG `Database` CR exists and reports `status.applied`; ensure the project database floor (`provision-project-env`: database roles, `IF NOT EXISTS`), the run plane (`reconcile-run-plane`), the credentials (PAT reused when present, `pat_secrets.rs::secret_name`; the verb writes the credential Secrets and owns them), CDC (`enable-cdc`, probe-guarded, `provision/src/sql.rs (publication probe)`) and the admin grants (`materialize-admin-grants`). On an environment that already has all of this, every ensure is a read. A crash anywhere here is repaired by applying again.
5. Expand. Update the policy name and route host columns of the environment row together, then reconcile the durability projection from the policy (R2); the readiness budget and drain bound used below are the declared policy's. Ensure every connection definition the document names: its instance exists and is enabled, its generation is current, and the declared release's bindings exist (`bind-connection`); retire nothing yet, because the live set still reads its own bindings (R22). With a release: install any package the environment has never had from its verified artifact, then run the package stage (§10.2) in the project database as the provisioner role. A failed stage stops here; nothing was written to Kubernetes. A backfill that stops on a lock stops here too, resumable by applying again.
6. Write. With a release: render the `release` values; when the chart version and the values, `audit` excluded, equal the last successful revision's, there is nothing for Kubernetes to converge on and the Helm call alone is skipped: steps 7 and 8 still run, so an interrupted apply resumes by observation and a connection-only or floor-only apply writes no Helm revision. Otherwise run `helm upgrade --install <name> release --version <chart version> -f values.yaml --skip-crds --wait --timeout <readiness budget> --rollback-on-failure --history-max 50 --description "apply by <actor>, approved by <approver>"`. Helm applies the templates, waits for the host Deployment's new pods within the policy's readiness budget, and on failure restores the previous successful revision itself (§4.3); the chart has no hooks. A Helm failure leaves the previous release serving, and the verb reports it. With `release = none`: skip step 7 and run `helm uninstall <name>`; Kubernetes begins terminating the hosts, each drains on SIGTERM (R20); step 8 then waits for the live set to be empty.
7. Readiness. Wait on each WorkloadDeployment to report `Ready`, which the verb does under either Helm wait strategy; then the check (§10.3). From here new admissions go to the new release.
8. Drain. The old release's pods are terminating, each finishing the runs pinned to it in its SIGTERM path (R20); Helm's wait did not wait for them, because a terminating pod is outside the Deployment's counted replicas. The verb waits for the live set to be exactly the declared release, or empty for `release = none`, up to the largest `terminationGracePeriodSeconds` the terminating pods carry; Kubernetes owns that clock, the verb only observes it. When the old pods are gone but runs are still pinned to the old release, those runs are stranded: the verb names them and their digest and exits non-zero; after a rollout `rollback` recovers them, after `release = none` the digest goes back in the document and is applied (R20).
9. Contract. Only when no pod of another release remains and no run is stranded: remove the bindings of releases no longer in the live set, and disable each instance the document no longer names that no surviving binding uses (R22); when a declared floor descends from the recorded one, or is the first for its installed package, and the live set is exactly one release with no run pinned to another, apply the contract SQL and record the floor (R13, R16), else say the floor is waiting and exit non-zero. Release the lock.

Step 6 is the one rollout write, the only Helm release write; the `Database` CR and the credential Secrets of step 4 are ensures that a settled environment reads and never changes. Steps 4, 5 and 9 are the Postgres writes, and none of them is about the deployment itself: the substrate, the document's rows, the stage, the floor. No transaction and no row lock spans the Helm write, and no Helm timeout spans a Postgres write; the one thing held across convergence is the session advisory lock (R19). Kubernetes RBAC makes `apply`'s ServiceAccount the only writer of the `release` chart. Promotion is a document: the staging file's digest in the prod file, applied; the digest is accepted because it is qualified (R7, R12), and whether staging is healthy at that moment is the operator's judgment, not a rule. A verb that dies anywhere leaves whatever serves serving; the next `apply` observes and continues. That is the whole cost of having no separate completion step and no record of the deployment.

### 10.2 The package stage

The stage is wamn's own by the §1 test, so `apply` runs it, not a Helm hook: a hook is awaited under Helm's `--timeout` (§4.3), which a resumable backfill cannot promise, and a hook puts wamn's lifecycle inside Helm's. Under the lock, the verb does, idempotently:

1. verify the predecessor: the installed package versions match the predecessor the stage evidence was made against; otherwise refuse and name the difference (today's recheck, `package_upgrade.rs::require_application`, reduced to this comparison);
2. write the release cache row `catalog.releases (manifest_digest, manifest)` for R if absent (R1);
3. apply the stage for each upgraded package: expand with synchronization triggers, or a resumable backfill, under the five-second lock timeout (`package-upgrade.md §7.3`; `apply_coordinated` unchanged in content). The installed version advances only after the last batch and the postcondition. Stage evidence and progress rows (`package_upgrade_qualifications`, `package_upgrade_stages`) are keyed by package artifact digest, predecessor release digest and evidence digest, replacing today's `manifest_sha256` and `qualification_sha256` columns;
4. `reconcile-package-data-access` for the packages of R.

Nothing else: provisioning, credentials, run plane, and CDC are `the first apply`'s and never run per release. Stage before write, so the schema is expanded before any pod of R exists; the predecessor keeps serving on the expanded schema, which `qualify-upgrade` tested (§14).

### 10.3 Readiness and the check

Rollout means "R is loaded and serving": the host's readiness probe reports ready only after the release is loaded and compiled, and the Deployment controller shifts no traffic before that. `helm upgrade --wait` waits on that Deployment. The verb then waits on every WorkloadDeployment of R to report `Ready` (today's `kubectl wait`, `upgrade_environment.rs::deploy`), whatever Helm's wait strategy covered. The readiness budget is one deadline, set when step 6 starts: Helm's `--timeout` is the whole budget, and the WorkloadDeployment wait gets what remains of it, so the budget bounds the rollout and not each wait in turn. Two controllers roll here: Kubernetes retires an old host pod once its replacement pod is ready, and the wasmCloud operator places the new release's role workload on the new host after the host registers; the old role workload can leave before the new one is running. The plan accepts that window as an availability characteristic of a rollout, measured by an Epic 5 acceptance test; if an application needs none, the fix is at the readiness seam, the host reporting ready only once its placed role workloads run, and never a pod-by-pod sequence in `apply`. Then the check: when the manifest names a check route, one authenticated request with the private bearer against it, which must be a read (`route_method` GET, `delivery/deployment.rs::route_method, authenticated_interaction`); a write is refused at qualification, because a retried write with a lost reply would be a replayed mutation. The check route is one optional field of the manifest (contract C); an http application with no safe read names none, and no application invents a GET for deployment's sake. When none is named, or R has no http role, readiness is the check. The check runs in the verb and leaves nothing in Kubernetes; `helm test` and its Job are gone (R6). A failed check is a failed `apply`: R serves and reports ready, the verb exits non-zero and names the route, and the operator chooses `rollback` or a fix; the verb does not roll back on its own, because Helm succeeded and the failure is the application's.

### 10.4 Staged and multi-step upgrades

The staged model on `main` is the migration model (R13): each `upgrade_stage` is one immutable package version, one release, one apply. The contract stage is not run with the release: it waits until no host serves an older release and no run pinned to one is in flight (`package-upgrade.md §7.3`; runs pin the manifest digest, R1), which is after the drain. It is declared, not commanded, and takes two applies, expand-before and retire-after (R22) as two visible steps (owner ruling 2026-10-09). Apply A keeps the current release and adds the contract version to the document's `floors`: step 9 applies that version's contract SQL under the current release and records the floor `(package id, version)` in the project database (R16) when the declared floor descends from the recorded one through `predecessor_version` and the live set is one release; until then the document is applied except for the floor, and `apply` says the floor is waiting. Apply B names the release that carries the contract version. The migration model has no recorded-but-not-run state, and the release-membership seal stays. A floor is irreversible, so a document that omits a recorded floor or declares an ancestor of it is refused at step 3. The recorded floor is what step 3 of `apply` enforces. Renaming `qty` to `quantity`:

| Step | Package | Phase | Authored | The stage | Serving |
| --- | --- | --- | --- | --- | --- |
| 1 | `wms@2.2.0` | `expand` | `ADD COLUMN quantity` in `migrations/` | applies it; the platform installs the synchronization trigger so the old release's writes to `qty` mirror to `quantity` (`package-upgrade.md §7.3`) | old release, then R1 |
| 2 | `wms@2.3.0` | `backfill` | `upgrade_stage.backfill.sql`: `$1` cursor, `$2` batch size, returns next cursor and complete (`manifest.k upgrade_stage`) | batches, one transaction each, cursor in `package_upgrade_stages`; resumed by `apply` of the same digest; the version advances after the last batch and the postcondition | R1 throughout |
| 3 | `wms@2.4.0` | `contract` | `DROP COLUMN qty` | apply A: the document keeps R2 and declares `floors = { wamn_wms = "2.4.0" }`; step 9 runs the contract SQL and records the floor once the live set is one release. Apply B: the document names R3 | R2, then R3 |

Custom logic lives in three authored places and nowhere else: the version's migration SQL, the stage's backfill SQL, and the stage's `preconditions` and `postconditions`, all in the stage grammar (`package-upgrade.md §7.3`). A transformation the grammar cannot express is refused by design (`:570`); the way through is an application command run under R1 before step 3, which is application code, not a migration. Widening the grammar is the open owner question on `wamn-5ihq.3`. Rollback between steps 1 and 3 is `rollback`; after step 3 the floor `wms@2.4.0` refuses R1 and R2, because neither is it nor descends from it (R16).

## 11. Failure, rollback, history, status

### 11.1 Failure

- Stage failed: nothing was written to Kubernetes; the previous release runs; the installed version is unchanged; the verb names the step.
- Backfill stopped on a lock: the installed version is unchanged, the cursor is kept; `apply` of the same document resumes.
- Helm upgrade failed: `--rollback-on-failure` restores the previous successful revision; Helm records the failed revision in its history; the previous release serves; `apply` again re-renders and re-applies.
- Rollout stuck past the timeout: the same as a Helm failure, since `--wait` failing is a failure of the upgrade. The Deployment reports `Progressing=False` after `progressDeadlineSeconds`; the WorkloadDeployment reports its conditions (`Artifact, Sync, Deploy, Scale, Ready`). The operator reads them with `kubectl`; wamn copies nothing.
- WorkloadDeployment not ready after Helm succeeded: R's hosts serve; the verb exits non-zero; the operator runs `rollback` or fixes and applies again. Helm did not fail, so nothing rolls back on its own.
- Check failed: as above; the verb names the route.
- Drain bound passed with runs still pinned to the old release: the old pods are gone, the runs are stranded (R20); the verb names them; `rollback` brings hosts that can claim them; applying R again strands them again. No verb fails a stranded run on its own.
- Verb died after the write: whatever serves, serves; the lifecycle lock went with the connection (R19); the next `apply` observes and continues. Permissions need no repair, because no deployment verb touches them (R18).

### 11.2 Rollback

`wamn env rollback <coordinate> --reason <text>` is sugar over `apply` (R8): it finds the previous intended release, the newest revision in `helm history` whose status is `deployed` or `superseded` and whose digest differs from the current one, skipping `failed` and `pending-*` revisions; synthesizes the environment's document from the authorities with that digest as `release` (what `show` prints, with one field changed); and runs `apply` on it as a phase under the same lock, with `--reason` in the Helm description. One deployment path: the same predicate (R16, R17), the same stage rules, the same readiness, the same drain. `helm rollback` is not used, for two verified reasons: it restores the previous revision's whole values, a projection of route host and platform images that are owned elsewhere and may have moved since; and with no revision it targets `currentRelease.Version - 1`, which after a `--rollback-on-failure` is the failed revision, not the previous intended release (`rollback.go`). Going back further than one release, or past what `--history-max` retained, is the same thing by hand: the older digest in the file, applied. A rollback is also how stranded runs are recovered: hosts of the restored release claim what was pinned to it (R20). Rollback is safe when the predicate holds: after an expand the old release was tested on the expanded schema (§14); during a backfill the installed version has not advanced (`package-upgrade.md §7.3`); the chart has no hooks, so nothing migrates on the way back. After a contract stage the dropped structures make releases below the floor fail at runtime, and only the predicate stops that. Permissions need nothing: each host expands the roots for the release it loads (R18).

By layer. The `release` chart is the only Helm release per environment and has no hooks, so a rollback of it runs nothing elsewhere.

| Layer | Owner | Rollback | Never touched |
| --- | --- | --- | --- |
| application | chart `release` | rollback: `apply` of the previous intended digest; predicate, `helm upgrade --wait`, check, drain; hosts and workloads return to the previous digest with today's route host, image set and connections | the schema, which stays expanded |
| environment infrastructure | the `Database` CR, applied by the verb | none needed: the CR spec is one object with no history; `apply` re-applies it; there is no reverse operation for roles, slots or credentials and the plan claims none | the database, its data, roles, CDC slots, PATs, Secrets |
| platform | `deploy/infra` charts | their own `helm rollback`, independent of every environment; followed by `apply` of the running release so the image set and the qualification match again (R15) | environments; CRDs stay installed |
| data and schema | PostgreSQL | none; forward only through expand, backfill, contract and the floors. A restore from a CNPG backup is a database operation, not a chart | — |

The floor is a row in the project database; no chart rollback changes it.

### 11.3 History

`helm history` of the `release` chart is the deployment history: one revision per Helm write, rollback included since it is an apply, with the chart version, from which the image set follows, and the digest, the actor and the approver in its values and the action in its description; an apply that changes no rendered value writes no revision (§10.1 step 6); a `--rollback-on-failure` adds a revision of its own. After a successful upgrade Helm marks the prior revision `superseded` (`pkg/action/upgrade.go`), so a successful revision is one whose status is `deployed` or `superseded`; `failed` and `pending-*` are not. Every `helm upgrade` the verb runs passes `--history-max 50`; Helm's default is 10, and the limit is a property of the command, not of the release, so it is stated on every call. abandon and `delete` end the history with the release (§12.2); an environment's history is the history of its current installation. No wamn table (R5).

### 11.4 Status

The platform UI reads status through a control operation with a read-only ServiceAccount over Pods, Deployments and WorkloadDeployments in `hosts`: the digest from the host Deployment's pod-template annotations, the rollout from its status, the workload conditions, the live set. Who selected and who approved are not there: they are in the Helm revision (§11.3), read with `helm history`, not by the UI. Current state only; no history of checks; no Secrets; no verb runs from a browser. The project screen that reads the saga today reads this instead.

### 11.5 Drift

Not detected in option A. `apply` of the same document re-renders and re-applies; Helm applies a no-op when nothing changed. Continuous drift detection is what option B adds (§17.3).

## 12. Environment creation, copy, abandon, delete

### 12.1 Create, copy, promote

None of these is a verb. Create is the first apply of a new document (§10.1 step 4 ensures the substrate: the row with its `instance_suffix`, the `Database` CR, the Postgres and identity steps; step 5 the connections; step 6 the release). Copy is the same document under a new coordinate: it copies deployment configuration, the release, the route host, the policy, the connection definitions and the floors, and nothing else; roles, members and grants are security administration in the project database and are not copied; credentials are provisioned, never copied. There is no source to read, no second lock, no ordering rule and nothing that can be half-copied. Promote is the same digest in another environment's document. The 15 and 17 saga steps, create-environment, copy-environment and promote become one verb reading one document, and nothing else. Release publication (admit-components, publish-release, push-release-manifest) is not environment work: a document names a release digest that already exists in OCI.

### 12.2 Abandon

Abandon is a document with `release = none`. `apply` of it skips qualification, stage and readiness, applies the document's connections like any other, must declare the recorded floors and can advance none (R13), and runs `helm uninstall` of the `release` chart under the lifecycle lock; the uninstall is what starts the drain, because Kubernetes begins terminating the hosts and each one finishes its pinned runs on SIGTERM (R20); the verb then waits, up to the drain bound, for the live set to be empty. Empty: it removes the uninstalled release's bindings and keeps every declared instance enabled (R22). Runs still pinned: it names them and their digest, retires nothing and exits non-zero; the Helm history is already gone, so `rollback` has nothing to read, and recovery is that digest back in the document and `apply`, which reinstalls on the bindings that were kept (R20). Hosts and workloads go; the `Database` CR, the Secrets, the environment row and every project-database row stay; the Helm history ends with it. It is not kept, because `helm upgrade --install` refuses a release whose history exists but has no deployed revision ("has no deployed releases", helm/helm#11553), so keeping it would need a reinstall path of its own. Applying a document with a release later starts a new history.

### 12.3 Delete

`wamn env delete <coordinate> [--data]` is the one verb that touches the database and the one destructive action no document can express, and it is re-entrant: every step is "if present", so a run that fails at any boundary is resumed by running it again. Under the lifecycle lock (R19), in order: `helm uninstall` the `release` chart if present, which starts the drain, each host finishing its pinned runs on SIGTERM (R20); wait, up to the drain bound, for the live set to be empty; if runs remain pinned to a release with no pod, name them and their digest and refuse here, the way back being that digest applied again (R20), unless `--data` was given, because deleting credentials and the database would make those runs unrecoverable and the operator has only asked to delete the environment; then revoke the credentials if present (today's `delete_project_env.rs` revoke path); delete the credential Secrets it owns if present; delete the `Database` CR if present and wait until it is gone; delete the environment row last, so wamn forgets the environment only after Kubernetes has finished with it. The CR carries `databaseReclaimPolicy: retain`, so deleting it leaves the PostgreSQL database and its data on the project `Cluster` (§4.4). With `--data` the verb patches the policy to `delete` before deleting the CR and waits for the CR to be gone, which CNPG reports only after the database is dropped; the operator's name must be given twice, and stranded runs do not stop it. What a retained delete leaves is an orphan for manual recovery, by design: the database's physical name carries the environment's `instance_suffix`, drawn once per provisioning so that "deleting an environment and recreating it under the same triple yields different physical names and the new environment cannot inherit whatever survived the delete" (`system-schema.sql registry.project_envs`, `provision/src/name.rs::project_env_database_name`). Applying the same document again therefore creates a fresh database; the retained one is reached by a database administrator with `psql` or a CNPG backup, never by a wamn verb, and the plan adds no tombstone to find it. A partially applied stage leaves the installed version unchanged by the stage rule (`package-upgrade.md §7.3`); staged progress (synchronization triggers, backfilled rows, a cursor) may remain in a retained database, and the installed version says which whole package it is at. A half-deleted environment is therefore a retained database plus whatever the failed step left, and the same verb finishes it; no second Helm release is needed to make deletion whole.

## 14. qualify-upgrade

`qualify-upgrade` keeps what only it can test and drops what `push-package` and `qualify-release` already test. Under the staged model it tests the expand stage on the scratch copy; a backfill stage for its batches and postcondition; the contract stage for the selected release's statements against the contracted schema, which is the floor rule.

| Step in `qualify_upgrade/mod.rs` | Keep | Why |
| --- | --- | --- |

### 17.3 Deferred: option B

Not now. When continuous drift detection or a pull-based deploy is wanted, add Flux and point a HelmRelease at the `release` chart with the values file committed to a repository; the `Database` CR becomes a manifest under a Flux Kustomization. The environment documents are already files, so B is: commit them, and `apply` commits the rendered values in step 6 instead of running `helm upgrade`. How writes are serialized and how convergence is awaited once Git owns the desired state is deferred with B; a process-local advisory lock cannot order Git writers, so option A's lock is not promised there. Nothing in option A is redone: the documents, the chart, the values and the readers are what B consumes. Two facts shape the choice. The chart version selects the image set (R15), so it needs no cluster read under Flux or Argo CD; Flux keeps standard Helm release storage and Argo CD does not, which matters only to `rollback`'s read of `helm history` (R8). A hand edit of the committed values bypasses the stage and the predicate exactly as a hand `helm upgrade` does today; the rule for B is that only `apply` writes that path, and nothing in the cluster enforces it. If a guard is wanted later, the host refusing to start when the installed stage is behind what its release needs is the place; not Postgres.
