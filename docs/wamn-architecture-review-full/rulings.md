# Implementation rulings

As of 2026-11-12. This file records each ruling that the implementation of `review-report.md` needs. The user delegated these rulings to the orchestrator on 2026-11-12. Each ruling has a number, the question, the decision and the reason. A later ruling that changes an earlier one names it.

The controlling principles, from the user, verbatim: "single responsibility, single source of truth, no rewrite, restructure or rename is too large. preference for deletion of all accidental complexity".

The testing rule, from the user: keep tests to a minimum, test only interfaces, never test the presence of a string or a file, never compare strings or files exactly, and avoid complex mocks.

## How the work runs

I1. Branch. All work lands on `worktree-arch-review`, which starts at `5d22e687a` (main at the start). The orchestrator pushes the branch to origin after each integration. Nothing merges to main. Reason: the user asked for frequent pushes for external review, and did not ask for a merge.

I2. Lanes. Each lane is a Codex `gpt-6.1-sol` agent at high effort in its own worktree under `.claude/worktrees/lane-*`, on a branch `lane/<step>-<letter>` from the current head of `worktree-arch-review`. A lane edits files and runs checks. It does not commit, push or run `bd`. The orchestrator reviews the diff, commits it in the lane worktree and merges it into `worktree-arch-review`.

I3. Review. Each finished lane gets a separate read-only Codex `gpt-6.1-sol` review at high effort. The review reads the diff against the brief, the report and these rulings. The orchestrator sends the findings back to the same lane before the merge (findings first).

I4. Checks per lane: `cargo fmt --check`, `cargo clippy --workspace --all-targets` in each Cargo workspace that the diff touches, and the unit tests of the changed packages. No live cluster run, no `kind` run, no deployment and no full `tools/test-changes` selection. A focused Postgres test can run when a SQL change needs proof, and the orchestrator runs it, because the lane sandbox cannot start Postgres.

I5. Build output. Lanes share one Cargo target, `~/.cache/wamn-target/arch`, as the disk rule requires. Cargo serializes on its lock. Before a test that reads files through `CARGO_MANIFEST_DIR`, a lane runs `cargo clean -p wamn-fixture-package`. The target is removed when the work stops.

I6. Tracking. One bead epic holds the work, with one child bead per step. A child closes on the commit that lands its step.

I7. Steps are epics. The user's instruction of 2026-11-12 ("you are not to stop after epic 1") treats the steps as epics. This answers question 28: the steps S0 to S13 are the epics of this work.

I8. Docs. Each step corrects the `docs/architecture/` pages that it changes, as the report requires. `docs/history/` stays as written. The Claude Doc of the review is not edited by this work.

## Open points of the report

R1. Signing-key rotation cadence (ruling 30): 30 days. The identity service keeps the previous public key for verification until the longest token lifetime after the rotation ends. Reason: one fixed schedule, and verification needs no second rule.

R2. Guest memory budget (ruling 35): the host takes one budget value from its configuration, with a default of 256 MiB per instance. S9 measures the fixture applications, and a measured peak above half the default changes this ruling. Reason: a value is needed to enforce, and the measurement belongs to S9.

R3. R-06 timeout between `in-progress` and `outcome-unknown`: the longest call, `MAX_HOST_CALL_DURATION` (30 s). A claim with no result that is older than the longest call is `outcome-unknown`. Reason: one source of truth for the bound, and no new setting.

R4. Question 40: `project_key` replaces `tenant_key`, and `current_project_key()` replaces `current_tenant_key()`.

R5. Question 41: the word rename (step S0) runs after S1 and S1b land, so that it does not rename deleted code.

R6. Question 42: yes. The error convention in `CLAUDE.md` changes from "a kind" to "a type", and error types use `ErrorType`, as `docs/history/kind-to-type.md` decided.

R7. Question 43: yes. "claim" alone means a write log claim, "JWT claim" keeps its standard name, a queue claim of a run becomes "lease", "scope" means the invocation scope record, "environment" means the hierarchy level, and "check" means a SQL `CHECK` constraint.

R8. P15 and P27 (step S1b): accepted. They delete code with no product caller, which the principles require.

W37. Postgres capability, crate names and dependency cleanup (owner, 2026-11-14). It replaces W36 and revises W30 and the earlier dynamic SQL ruling.

Postgres capability scope. The capability is the caller identity on the transaction, the host operation transaction with its idempotency claim and write log, and the pools. Everything else moves out. The authorization reads (`PRINCIPAL_GRANTS_SQL`, `USER_OPERATION_PERMISSIONS_SQL`, `ENVIRONMENT_INACTIVE_SQL`) move to `wamn-authentication`, which passes the user id and role to the capability. Next-number and peek-number become guest SQL in the host transaction, and their host code and WIT functions go. The run queue SQL moves to `wamn-workflow`, the lease SQL to `wamn-connections`, the event admission SQL to `wamn-events`, and the file collection SQL to the owner of the file collector. `credential_exactness` is deleted.

Identity. At transaction start the host sets `app.identity` to a signed token (user, role, expiry) with `set_config(..., true)`. The database reads the identity only through one SECURITY DEFINER function. That function checks an HMAC (pgcrypto) with a key that only it can read, and it caches the result for the transaction in a temporary table that the definer owns. Triggers and row policies call it as `(SELECT fn())`. The token expires at the invocation deadline, which is 30 seconds at most. The host clears `app.identity` when a connection returns to the pool. History triggers and row policies stop reading `current_setting('app.user_id')` and `current_setting('app.role')` and call the function.

Interfaces. There are two separate SQL interfaces. Dynamic SQL has `query` only and serves analytics-type queries. It runs on the `wamn_query` login in a host read transaction (amended by the owner on 2026-11-14, per W38). `wamn_query` is SELECT-only, apart from INSERT on `platform.tx_identity`. Applications can import it, so it is not in `APPLICATION_DENIED_INTERFACES`. Operation SQL has `query` and `query-batch` in the host transaction (`operation-transaction()`) on the `wamn_app` login. Both use the upstream `wasmcloud:postgres` result shape: column names, a stream of rows and a closing result. `row-set` and `run-stream` go. Guest `begin` and its transaction resource go, and so do `execute`, the transaction and the cursor of the old client interface. Admitted statements go: statement resolution, verified bytes, value and result shape checks, statement sets and digests in the release manifest and component facts, and `require_declared_statement`. The capability then no longer depends on `wamn-compiler`. Composition does not change: composed applications share the host operation transaction.

Pools, limits and SQLx. One map, keyed by project and login, holds the pools, and the split between `guest_pools` and `platform_pools` goes. The row limit is deleted, because streaming bounds memory and `statement_timeout` bounds time. The privilege check in `after_connect` is deleted, and `statement_timeout` stays. SQLx stays everywhere (U2). The build checks generated SQL, and authored guest SQL is checked when it runs.

Connections and transactions. The product does not enforce "no external call inside a transaction". It is a documented development practice. The W30 build refusal and its tests go. A component declares its connections, not each operation, so the per-operation declarations and their resolution check go.

Crate names (ruling 26). One crate serves one concern and takes its name, with no "capability" prefix or suffix. `wamn-postgres-capability` merges into `wamn-postgres`. `wamn-events-capability` merges into `wamn-events`. `wamn-http-capability` becomes `wamn-http`. `wamn-integrations` merges into `wamn-connections`. `wamn-capability-authority` becomes `wamn-authority` and takes the `invocation` and `connection_binding` modules from the Postgres crate, so other capabilities stop depending on `wamn-postgres`. `wamn-blobstore` and `wamn-authentication` keep their names.

Dependency cleanup. `wamn_platform_install::lifecycle_lock` moves to `wamn-registry`, and `wamn-workflow` drops `wamn-platform-install`. A test that reaches a crate above its own crate moves to that crate or to the journey tests (11 cycles in `cargo metadata`). After the change, no crate's dev-dependencies reach a crate that depends on it. W38. Caller identity: the first insert wins (owner, 2026-11-14). It replaces the identity part of W37. The signed token, the HMAC key, pgcrypto, the token expiry and the clearing of `app.identity` at pool return are all dropped.

Schema. Every project database has the platform-owned table `platform.tx_identity` (UNLOGGED), with `xid xid8 PRIMARY KEY` from `pg_current_xact_id()`, `principal_id uuid NOT NULL` (amended by the owner on 2026-11-15: every call carries the principal that acts for it, which is a user, an API service principal, a platform component principal or the run's principal), `role text NOT NULL`, `application text NOT NULL`, `operation text` and `runner text`. The platform owner role owns it. `wamn_app` and `wamn_query` get INSERT only, and no application login gets SELECT, UPDATE, DELETE or TRUNCATE. A BEFORE INSERT trigger refuses a row unless `NEW.xid = pg_current_xact_id()`, so a transaction can write a row only for itself. The table is UNLOGGED because a row matters only while its transaction runs: it writes no WAL and is truncated on a crash.

Reading. `wamn_authority.current_identity()` returns `platform.tx_identity`. It is SECURITY DEFINER and STABLE, the platform owner role owns it, and it selects the row where `xid = pg_current_xact_id()`, or NULL when no row exists. Small accessors sit on top of it: `current_principal_id()`, `current_role()` and `current_application()`. History triggers and all row policies stop reading `current_setting('app.user_id' | 'app.role' | 'app.application' | 'app.operation' | 'app.runner')` and call these functions. Policies call them as `(SELECT wamn_authority.current_principal_id())`, so Postgres evaluates them once per statement. There is no other cache, because the primary key lookup is the cache. A policy or trigger that finds no identity refuses.

Migrations (amended by the owner on 2026-11-15). Migrations write no `platform.tx_identity` row. If no row exists for `pg_current_xact_id()` and `current_user` is a platform login, `wamn_authority.current_identity()` returns the component principal of that login from `platform.login_principal` (login name to principal id). The platform owner role owns that table, and no application login gets a grant on it.
